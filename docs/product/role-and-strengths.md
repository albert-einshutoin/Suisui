# SoloPM Role And Strengths

SoloPM is a Local-first personal AI PM for macOS. Its role is to turn captured work, project documents, due dates, and local context into reviewable next actions without moving ownership away from the user.

## Strengths

- Local-first data boundary: projects, tasks, settings, and release evidence stay on the Mac unless the user chooses a provider or connector.
- review-before-execution: AI and MCP flows propose task changes, schedule blocks, artifacts, and plans before write actions run.
- MCP-ready extensibility: external tools can be connected through explicit registration, audit history, structured content validation, and paid execution boundaries.
- complete task lifecycle harness: task creation, content editing, status movement, automation review, approved local execution, and destructive delete confirmation are tracked as one E2E contract so product-critical CRUD does not regress silently. Approved local execution leaves a task-detail execution note plus a redacted execution receipt, so a status move alone cannot masquerade as running the reviewed task content and tests can inspect the reviewed payload without exposing copied tokens.
- VoiceOver-aware workflow: source anchors, pseudo VoiceOver focus-path checks, runtime AX smoke, and manual VoiceOver evidence are separated so accessibility regressions are caught early without pretending automation replaces assistive-technology review.
- document-scoped automation: selected docs can produce task drafts, status/due-date proposals, release notes, PR plans, and draft artifacts with document reasons and approval gates.
- complete document deliverable harness: document-scoped automation must prove preparation checklists, draft artifacts, release notes, and PR plans independently before the E2E harness passes; external-source-only context stays excluded until connector-specific approval exists.
- task automation selection reasons: priority and due-date tradeoffs are carried into review-only LLM plans so the user can inspect why work was selected before approving any update. High-priority undated work stays ahead of lower-priority future work, while tasks outside the configured lookahead window are held back from LLM review. The review cadence can be manual, hourly, daily, or weekly, and overdue or due-today work can use a separate urgent review cooldown so low-frequency automation does not hide urgent tasks; the extra provider call only includes the urgent candidates. Manual cadence is explicit user-triggered review, so scheduled automation runners cannot spend provider calls when the user chose manual frequency. Daily LLM budget is evaluated against the configured calendar day, so yesterday's session or persisted call count does not permanently block today's due work. The LLM request also carries the configured cadence, task cap, daily call limit, remaining budget, lookahead, urgent cooldown, and direct-execution boundary. When a selected task is backed by approved documents, the ProjectBoard review request can also carry source-bound document deliverables such as preparation checklists, draft artifacts, release notes, and PR plans as draft-only approval-gated outputs with redacted source previews. The Task inspector mirrors those draft deliverables and source previews before execution, so users can inspect the same document evidence that provider planning received. The provider request reapplies the task cap, daily LLM budget, priority/due/status eligibility, priority/due/id ordering, review-only approval flags, document source-preview binding, file-deliverable-only boundary, and duplicate suggested output paths at the API edge so future non-planner entry points cannot send extra task content, send done/blocked or out-of-window work, overstate remaining budget, put lower-priority future work ahead of urgent work, turn a review request into direct execution, send two drafts for the same file, or smuggle task/status mutations through document outputs. Selected task facts and document deliverables are sent as fenced redacted JSON so task title/detail text, source previews, and document rationale stay content, not automation instructions, and copied API keys or tokens do not leave the Mac in provider context. Approved local execution keeps the remaining reviewed tasks in queue and appends redacted execution receipts, so a multi-task review can be executed item by item without losing proof of what ran.
- Practical solo operator cockpit: Today, Inbox, Project Board, Done analytics, Settings, and local assistant affordances stay close to daily execution rather than becoming a generic chat surface.

## Product Boundary

SoloPM should not silently execute destructive actions, leak provider keys, or treat generated summaries as proof of manual checks. High-risk work stays explicit: review the plan, inspect the documents used, approve the action, then run it.
